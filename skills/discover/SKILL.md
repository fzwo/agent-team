# Discover

The owner arrives with a vague idea; this skill ends with a written brief, a recommendation per question, and the owner's decisions recorded. The questions it asks are the ones that are expensive to answer late: whether the thing already exists, whether the hard part is possible, where it should run, under which licence it goes out and how it earns. The decisions are the owner's; the research and the honest reading of it are this session's.

**Principles.** Research runs in subagents with fresh context, one per question, so the session stays thin; the `deep-research` skill does the landscape where it is available. Every claim in the brief carries its evidence (a link, a dated observation, a prototype result) or is marked as the session's judgement. Facts about platforms, stores, prices and licences change: date them. Nothing is invented: a product the research did not find is "not found", not "none". If the space is crowded, the hard part infeasible or the licence choice closes a door the owner wants open, that is the first line of the brief, not the last. The owner's taste calls (name, look, what it is for) are prepared, not made.

## Steps

0. **The repository, if there is one.** The owner usually creates the repository on GitHub first, with a description and nothing else. If the owner names it, or the working directory's origin is it (ask when unsure: an origin is not the idea's repository just by being there), work in it: clone it where the session runs if it is not there (`gh repo clone <owner>/<name>`), read the description from the repository's metadata (`gh api repos/<owner>/<name> --jq .description`; the REST form, since GraphQL is not available from every session) as the first line of the idea (empty: the interview asks), and deliver the brief as a branch and a pull request, so it is in the repository's history before any code. A repository with no commits has no base for a pull request: make the first commit on its default branch (`gh api repos/<owner>/<name> --jq .default_branch` names it even when no ref exists yet; a README holding the description alone), push that once, and say so in the hand-off; it is the one push to a default branch this skill makes, and the brief then goes on a branch. Do not create a repository unasked: that is the owner's act; when the owner asks for it in so many words, `gh repo create` with the description they give. Without a repository, write the brief in the working directory and say in the hand-off that it moves into the repository when the owner creates it. This skill needs the web and GitHub, not the Mac: a cloud session with the repository attached is the natural place for it. A prototype that needs Xcode, a simulator or a device needs the Mac; before the project exists there is no channel to a Mac session, so ask the owner to run that part in a session on the Mac and bring the result, and say what to run.

1. **Interview, one message.** At most five questions, each answerable in a sentence, numbered: what it should do and for whom; what the owner already knows, has tried or has seen; the constraints they hold (platforms they own or care about, time, money, must-haves, must-nots); what success looks like in a year (a hobby that works, a product with users, income); what it is not. Do not ask what research can answer. If the owner's answer is "I don't know" to any of them, that is an answer: the brief explores it.

2. **Research, in parallel subagents.** Each gets the interview's answers and one question, and returns findings with sources:
   - *What exists.* Products, open-source projects and papers in the space; the three closest, with what each does, what it does not, what its users complain about (reviews, issues, forums), its licence and its price. What the idea would add that they lack, in the owner's words, not marketing's.
   - *Feasibility.* The two or three hardest technical parts, and for each whether it has been done, by whom, with what. Where a day's throwaway prototype would settle the riskiest one, build it under the session's scratch directory or `$TMPDIR`, never in the working directory (the future project folder, which `team-init` will set up), measure, and report the numbers; delete it afterwards or say where it is. What the platforms allow and forbid (APIs, entitlements, store review rules, background limits), with the rule's date.
   - *Platforms and distribution.* Where the intended users are; what each platform costs in work, money and ongoing obligation (store fees, review cycles, notarisation, hosting); native, web or both; what the owner's existing skills and machines favour. A recommendation with the order in which platforms could follow.
   - *Licence and commercialisation.* The options as a short table: open-source licences grouped by what they permit (permissive, weak copyleft, strong copyleft), source-available, closed; what each means for contributions, forks, store distribution, trademarks and later changes of mind (a licence once granted cannot be withdrawn from what was released under it). The ways it could earn (paid, free, freemium, subscription, support, dual licence) and which licences each goes with. Where the owner's answer to "success in a year" points.
   - *Name and footprint.* Whether the working name collides (products, trademarks in the owner's markets, domains, store listings, package registries), as a dated check, with the caveat that a trademark search by an agent is a first look, not clearance.

3. **The brief.** Write it from `templates/discover-brief.md` (in the plugin, `${CLAUDE_SKILL_DIR}/../../templates/`) as `discovery-brief.md` at the root of the repository, committed on a branch and pushed, with the pull request opened now (the owner's invoking this skill is their consent to that branch and pull request, which a cloud session's own rules would otherwise have it ask for), so the owner reads the brief there (or, without a repository, in the working directory). One page per section, appendices for the long lists. Its "Product" section holds the four headings `team-init` copies into `PRODUCT.md` (What it is for, For whom, What it is not, Principles: the last distilled from the owner's must-haves and must-nots, marked as proposed until the owner confirms them), and its decisions include the profile (`apple`, `web`, `none`). For each question: the findings, the recommendation and its reason, the alternatives with what would make them the better choice, and "what would change this". The first section is the verdict in three lines: go, go with changes, or don't, and why, marked as the session's reading.

4. **Decisions.** The last section lists the decisions the owner has to make, numbered, each answerable in a word, each with the recommendation, as `reference/messages.md` of the team-process skill asks for questions to the owner (the report footer does not apply: there is no state file yet). Send that list as the message to the owner, with the pull request's link. Record the owner's answers in the brief's Decisions section with the date, as a commit on the same branch; an answer that overrules the recommendation is recorded with the owner's reason when they give one.

5. **Hand-off, and stop.** The brief is the deliverable; with a repository, the pull request that carries it, which this session merges once the owner's decisions are recorded in it (the brief is the owner's own answers and research for them; it needs no review round), the only merge this skill does. Do not set the repository up for the process, do not run `team-init`, do not start building: the decision to start a project is the owner's, made looking at the brief. When the owner says go, the repository is cloned onto the machine that runs agents and set up there (the README's "a repo that is not there yet"), and `team-init` reads the brief: the profile and platforms, the "Product" section for `PRODUCT.md`, the licence decision for the `LICENSE` file, and `ROADMAP.md`'s Now, Next and Not now from the first version's scope and what was parked.

A later `discover` on a project that exists (the direction in doubt, a pivot, a new product line) runs the same way and writes `discovery-brief-<date>.md`; the earlier brief stays as the record of what was believed then. At its start the session writes the product's line under the roadmap's Products as "in discovery" (a housekeeping edit; the owner's invoking the skill is the decision it records). Its decisions list ends with the roadmap's lines it proposes: the product's status (active, or not at all), the first version's must-dos for Now or Next at the place the owner names, the parked items for Not now; once the owner has decided, the session writes them into `ROADMAP.md`, quoting the decision with the date, as the last commit on the brief's branch (the brief's pull request is the owner's own decisions, the roadmap lines among them) or by a housekeeping PR, since without that step a new product line left no trace in the direction (eight work issues filed by hand, the parked items in no "Not now").
