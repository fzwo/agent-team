# A shift

This skill is the engineering role's; it sets `Role: engineering` for the session regardless of CLAUDE.md.

If the argument is `end`: finish the piece of work you are on; wait for your running builders or stop them (a builder that reports after the end would wake the ended session, which could then review or merge beside the new shift: a shift ended with a builder still holding a simulator and uncommitted work in its worktree, and the next shift had to coordinate by message); stop what you and your builders left running (`ps -axo pid,ppid,etime,command | grep -F <repo path>`, the same for the scratch paths, and `grep -F watch-github.py`, since a watcher's folder is its cwd and not on its command line; wait loops and watchers started with `&` are the usual leftovers; another session cannot stop them later, and the owner should not have to), then, on an Apple-profile machine, run `tmp-sweep.sh --delete` and keep its counts for the report (the toolchain debris in `$TMPDIR`, `reference/profile-apple.md`; after the leftovers, so no build of yours holds a lock file), open the shift's notes PR if any notes were recorded and take it through its low-tier review and merge (or, if time is short, leave it open and list it under "In flight"), write `.agent-team/state.md` (what is in flight, what is next, the promises made in issues under `Promised`, what a fresh session would not know), set its `Shift:` line to "<N> ended <date>", push it on a branch and merge it as housekeeping, report with the footer in `reference/messages.md` of the team-process skill plus `Plugin: <version>` from `agentlock version` (a session keeps the plugin copy it started with, so a long session can be several releases behind; the line makes that visible), start your successor when the shift is due one (below), and, if the shift found something about the plugin itself (a script that failed, a rule that misled or was missing, a cost that surprised), send it to the plugin's maintainer through the channel named in CLAUDE.md's `Plugin feedback:` line (its fallback when the first tool is missing from the session; when the fallback is an issue, file it on the repository that line names and nowhere else, since a plugin's install repository can be public and feedback names the project's threads), most useful first, each point from something that happened this shift; when there is nothing to say, or no such line, send nothing. Then stop.

**The successor.** A shift that ends because its context is spent while the queue still holds work starts the next shift itself, unless CLAUDE.md says `Shifts chain: no`, or says `Shifts chain: max N` and this shift's `Shift:` line carries `chained k` with k ≥ N, or N is 0 (k shifts in a row have started themselves since a person last started one; the cap is the owner's bound on what a long queue may spend unattended): after the state file with "ended" is merged and the leftovers are stopped, run `shift-start.sh <repo root>` (on the PATH in a session; `scripts/shift-start.sh` in the plugin) as a Bash command with the tool's longest timeout (600000 ms) or as a background command, since it waits up to ten minutes for the new shift's first report; if the tool cuts it off, the tmux session survives, and `shift-start.sh --began <N+1> <repo root>` says whether the successor has started (by its exit code: 0 started, 1 not yet; it prints only when origin/main cannot be fetched). The script refuses while origin/main does not yet show your shift ended, which is the housekeeping merge still landing: wait for it (`gh pr view <n> --json state`) and run the script again. Then one more message, after the script has answered: where the successor runs (the script prints the tmux session), or that it failed and why, so the owner can start it by hand. A shift that ends because the queue is empty, because everything left waits on the owner, or because the owner said to end, starts nothing: the chain ends when the issues run out. Your own session stays open in the app after the end, idle, until the owner archives it there (archiving leaves the process running; the next start closes archived sessions); when CLAUDE.md says `Shift sessions: close`, pass `--close-ended` and the script closes it ten minutes after the successor reports its start (`--close-after <minutes>` changes that; the app then shows it under Archived, still readable), so send that last message at once.

**Started as a successor.** When your first message is `/agent-team:shift chained`, the previous shift started you. Write your `Shift:` line as `<N> started <date> chained <k>`, where k is one more than the `chained` count on the previous shift's line (1 when it has none), and keep `chained <k>` on the line when you end. A shift a person started writes no `chained`.

**A message after the end.** When the owner writes to a session whose shift has ended, that session does not open a new shift in itself (a session is a shift, and shift-start.sh reads the state file to number and name the next one): a small request that needs no builder and no watcher is done as it is, with the `Shift:` line untouched and without touching the checkout (no pull, checkout, commit or branch there: the successor may be working in it; a request that needs any of those is a piece of work); a piece of work is answered by starting the successor as above, with `--not-chained`, and saying so (an owner's request is a person's start: `Shifts chain: no` does not stop it, and the successor writes no `chained`, which resets the count), or, where the script cannot run, by pointing at it.

Otherwise start one:

1. Bring `main` up to date first (`git pull --ff-only origin main`); the previous shift's state file was merged on GitHub. If that pull fails (the checkout is on another branch, has uncommitted changes, or cannot fast-forward), do not force anything: `git fetch origin main`, read the state file from `origin/main` (`git show origin/main:.agent-team/state.md`), say in your first report what blocks the checkout, and sort it out before the first piece of work (a stray branch gets checked out of the way, uncommitted changes that are not yours are reported, never discarded). Read `.agent-team/state.md`. Take the number after `Shift:`, add one, and write it back as `Shift: <N> started <date>` in the same housekeeping commit as the rest of the shift's first state update. If there is no `Shift:` line, this is shift 1: say so, and that the owner can set the line to another number. If the line shows a shift started and not ended, check whether that shift is alive: `tmux list-sessions -F '#S' | grep '^<Project>-shift-' | grep -vx '<your own session name>'` (the name is the title `<Project> shift <N>` with every character outside letters and digits turned into `-`, as `shift-start.sh` names sessions, so yours is `<Project>-shift-<your N>`; any other session of the project may host the running shift, since a session that opened the next shift in itself keeps its old name; it may also be an ended shift's leftover, which `tmux attach -t <name>` shows in a moment), or, for a shift not started by the script, a `claude` process for this folder other than yourself and other than an ended shift's session, which lingers by design; if it is, say so and stop; if not, it died without ending, which is the normal failure: note it in your first report and carry on. Write the `Shift: <N> started <date>` line and merge that housekeeping commit before any other work, since `shift-start.sh` reads the start from it. Say in the first line of your first visible message, not in your thinking: "<Project> shift <N> started" (the project name: CLAUDE.md's first heading unless it is the plugin's own "Team process" or "how this repo" heading, else the repo folder's name; a colon and what follows it are dropped, as `shift-start.sh` does).
2. One-time housekeeping, only where missing: the "Review audits" section in the state file (from the plugin's `templates/.agent-team/state.md`); the `Review model, high tier:` line in CLAUDE.md (default `session`, meaning the session's model; the owner may name another); on an Apple-profile machine, the `Toolchain skills:` line in CLAUDE.md (team-init's step: export the toolchain's agent skills to a scratch directory, copy the subset the project needs into `~/.claude/skills`, record the names and the Xcode version on that line), for a project set up before the plugin carried it; when skills are already installed and nothing says which Xcode they came from, re-export once rather than guess, since the check in step 3 compares against this line from now on.
3. Follow the team-process skill from step 1 of its engineering loop: start the watcher as a background command, read the state file, run the sweep at the start of a shift (its own section in the skill: unanswered questions, decisions without an issue, threads quiet after a promise), check the inbox, take the next item from the roadmap. Read `agentlock status`: a live lock or waiter whose owner carries a builder's `:name` suffix, or whose reason names the previous shift's work, belongs to a builder of the ended shift that still runs (the owner id does not say which session it is); do not take over its resource, ask the owner or the previous session, and record it under "In flight". On an Apple-profile machine, compare `xcodebuild -version` with the Xcode version on CLAUDE.md's `Toolchain skills:` line (written by team-init, or by step 2 above when it was missing); on a change, re-export them (team-init's step) and update the line, as housekeeping. On an Apple-profile machine the start's disk check is `df` against the floor and `tmp-sweep.sh` for the temporary directory's entry count. Every builder gets a lock name in its brief. The state file's "Updated" line names the plugin version you run, from `agentlock version` (`Updated: <date> by <role>, plugin <version>`); a session keeps the copy it started with, and when the watcher reports that a newer one is installed, say so in your next report: the owner decides whether this shift ends early so the next one runs it.
4. Work the queue until it is empty, everything left waits on the owner, the owner says to end, or your context passes about 600k tokens; then do the `end` steps above (the context case with work left is the one that starts a successor).
