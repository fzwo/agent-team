# Profile: apple (iOS, macOS, or both in one repo)

Project-specific values (simulator model, board size, device names, languages, text sizes) live in the repo's CLAUDE.md under `Profile: apple`, not here.

## Observing the build

- Screenshots come from one fixed simulator at the boards' size, declared in CLAUDE.md (for example iPhone 16e, 390 × 844 pt), in the same states as the boards, light and dark, plus the variants CLAUDE.md lists (languages, largest text size) where a board exists for them.
- Screenshots come from a device only for system UI and motion.
- Files go to `design/built/<date>/`, named like the matching board (`home-light.png`, `home-dark.png`, `settings-de-light.png`, `home-large-text-light.png`). A clip of anything that moves goes next to them.
- The "Built" report lists which screenshots changed since the last round; design looks only at those.
- A macOS app: screenshots of each window at the board size from CLAUDE.md, same naming, from a clean desktop. The macOS window takes the `ui` lock while it is on screen.
- Both platforms in one repo: one `design/built/<date>/ios/` and `.../macos/` folder; boards are likewise per platform or shared, as DESIGN.md says.

## Locks

| Resource | Taken for |
|---|---|
| `sim:<name>` | Booting, installing on, launching in, screenshotting, or recording a simulator, and `xcodebuild test` runs on a simulator-family destination, which boot one. One simulator at a time per session; shut it down when done. Hosted unit tests may run on any idle simulator under its own `sim:<name>` lock (a second device on the machine took a shift's unit-test load off the board's simulator); on-screen checks belong on the board's simulator. Name the test simulator in the builder brief, or builders default to the board's and the split erodes. At most two test runners at once on a 16 GB machine: a second runner already pushed the load to 150 and made timing suites flaky; when both simulators are active, timing-sensitive suites run under `quiet` |
| `device:<udid>` | Anything on a physical device: install, launch, logs, screenshots, and `xcodebuild test` runs with a device destination (which take `sim` as well, since the rule cannot tell the two platforms apart after the quote cut) |
| `ui` | Anything that takes the screen or keyboard focus from the owner: screen recording, driving the simulator window or a macOS app window, `osascript`, the Accessibility Inspector. A headless `xcodebuild test` on a simulator does not; it takes `sim`. A macOS test run (`platform=macOS`) drives a window and takes `ui` alone |
| `quiet` | A measurement that needs the machine to itself: performance, memory, battery, timing, background-task behaviour. Waits for every other lock, then blocks everyone else's heavy work until released, the holder's sibling builders included; the holder runs the measured commands as `AGENTLOCK_AS=<name> agentlock with quiet -- <command>` |

The hook config (`guard.conf`) maps `simctl`, `devicectl`, `screencapture`, `xcodebuild test` and the like to these. Take the lock with a reason and a TTL that covers the whole step, a UI test's time allowance included: a hung UI test once retried its interruption handler for 39 minutes, the lock lapsed under it, and another agent took the simulator while it was still being driven. Give UI tests an `executionTimeAllowance` and run them with `-test-timeouts-enabled YES` (Xcode 27.2, 2026-11). Shut the simulator down and release before the report.

Under load, timing tests lie about PRs: with four to six agents running `xcodebuild test`, load averages of 300 to 470 made real-time audio tests fail in every review round of PRs that did not touch audio. Before attributing a timing-test failure to a PR, rerun it under `agentlock with quiet` on `main` and on the branch (three minutes, in that shift): a failure on both is the load, a failure on the branch alone is the PR. One failure in a known wall-clock suite that passes alone, in a PR that does not touch the code the test times, is a flake to record in the round summary, not a finding and not a rerun of the whole suite (a PR that touches that code gets the `quiet` comparison above); the project's CLAUDE.md lists its known wall-clock suites, and the lasting fix is an injected clock for each, filed as an issue (the first project did one after a shift in which nearly every full run on a loaded machine lost one such test). A measurement that repeats runs (a flake rate before and after, a load test) holds no shared test simulator for its whole span: it takes `quiet` for a bounded window, or runs in batches and releases between them; a builder once waited the full 30 minutes its project's wait cap allowed, behind a 90-minute measurement on the test simulator, and the hand-back cost little, but the wait was avoidable.

## Devices

- Back up the app's database (or container) before each install on the device; keep the backup until the piece of work merges.
- Launch muted. Never touch or dismiss system dialogs; stop and ask instead.
- Do not attach a debugger (`lldb`) to the device build; use logs.
- Measurements of background behaviour (background tasks, battery, memory of the speech model) are per project and belong in CLAUDE.md with their method.

## Builds and disk

- One derived-data folder per target, reused across branches (`-derivedDataPath` fixed per target in the build script), never one per branch.
- Keep at least 20 GB free; Xcode needs headroom. Each simulator has its own caches (one simulator's poster cache regrew 27 GB in fourteen hours of test runs), so with two simulators the shift's disk check must know which cache folders belong to which, or the second fills the disk unseen. Check at shift start and before a build; clean up by exact name, never by pattern. The one exception is the plugin's `tmp-sweep.sh`, which removes known toolchain debris from `$TMPDIR` by name shape, content and age (see below).
- **The temporary directory fills with toolchain debris that macOS clears only around a reboot**, and an agent Mac stays up for months. Seen on 2026-11-15 after 88 days: 61,173 entries, 23 GB; SwiftPM on Xcode 27.2 leaves about five `TemporaryDirectory.XXXXXX` folders holding a lone `.keep-directory` per build or test run (up to 11,600 a day on a busy shift), `.lock` files named after scratch paths that no longer exist (the script does not decode the path; it removes a lock file only when it is a day old and no process holds it open, and skips the class while a Swift or Xcode build tool runs), and `ibtoold-<pid>` folders of finished Interface Builder tools, each an `IB/` of named pipes and nothing else. They weigh little, but past a few tens of thousands of entries `ls` and globs fail and every listing is slow; the problem shows as a count, not as size. A fourth shape weighs much: Instruments and `xctrace record` write their `instruments_….ktrace` bundles to the same directory and never remove them, 30-40 MB per Time Profiler run and 4-6 GB per Animation Hitches run (59 had piled up by the middle of one shift). At shift start run `tmp-sweep.sh` (it reports the entry count and the debris, and warns above 10,000 entries) and at shift end `tmp-sweep.sh --delete`, which removes only those four shapes, older than a day, and says what it removed; put the counts in the report. Caches the sweep does not touch grow too: CoreDevice's install cache took about 800 MB per device install (Xcode 27.2, 2026-11), pruned by the project's own rule after each install. A busy day makes more than 10,000 folders, and a day-old age leaves the last day's in place, so the start's warning is routine after such a day; a project may give the end run a shorter age (`--age-hours 2`: a SwiftPM scratch folder lives for one build) once no other agent builds on the machine at that hour. The first run after months of debris forks twice per folder and takes minutes: run it with a long timeout or in the background. The bytes in that directory are usually the project's own (per-worktree build folders, app copies, device backups): those are the worktree hook's and the project's shift-end rule's, never the sweep's. A project may instead give builds a private `TMPDIR` under the session's scratch (`TMPDIR=<scratch>/tmp swift test`), so the debris goes with the scratch; then anything the project means to share across sessions (a check-build cache) needs an explicit path, not `$TMPDIR`.
- Anything the project keeps per worktree outside the worktree (build folders under `$TMPDIR`, caches named for the checkout's path) is removed by the project's `.agent-team/hooks/worktree-removed` hook, which `pr-cleanup.sh` runs with the worktree's path before removing it. The hook computes exact names from the path and never globs, so it cannot touch another session's live folders. A project that caches per checkout must have this hook, or the caches outlive their worktrees.
- **Instruments and traces.** No Instruments capture with less than 40 GB free on the Mac. On a device, Time Profiler alone with a time limit, never all processes with os_log or os_signpost: raw trace data ran at about 2 GB per 10 seconds and filled the phone.
- **The simulator's window is tool-version bound; `simctl` is not.** `simctl` (boot, launch, `io screenshot`, `recordVideo`) needs no app open and is what screenshots and clips use. Which app shows a simulator window, how it is opened, and where the screen sits in it change between Xcode versions, so those facts live in the project's CLAUDE.md with the Xcode version next to them, and a shift that finds them wrong updates them there, not here. Open the app from inside the selected Xcode (`xcode-select -p`), never by a bare name that an older install beside it may answer. Anything that depends on window geometry (`cliclick` positions, drag coordinates) is re-measured after an Xcode update. Before deleting an old Xcode, check that no running process lives inside it. Dated example, Xcode 27.2 (2026-11-03): there is no Simulator.app; DeviceHub (`com.apple.dt.Devices`) shows the device's screen beside a sidebar, after the device is selected there.
- **The toolchain ships its own agent skills; use them, re-export them after each update.** The skills a toolchain writes for agents are the vendor's current guidance for its SDK, and they go stale with the SDK, so they are exported from the installed toolchain, not copied into the repository (the vendor's text, and it would be republished with the project). Team-init exports them to a scratch directory and copies the subset the project needs into the machine's user skills directory; the project's CLAUDE.md records the names and the toolchain version on its `Toolchain skills:` line, and the shift's start compares that version with the installed one and re-exports on a change. Briefs name the matching skill for work in its area. Dated example, Xcode 27.2 (2026-11-17, reported by the first project's engineering agent): `xcrun agent skills export --output-dir <dir>` (with `xcode-select` pointing at Xcode 27) gave eleven skills, namely `swiftui-specialist`, `swiftui-whats-new-27`, `app-intents-specialist`, `app-intents-whats-new-27`, `xctrace`, `device-interaction`, `modernize-tests`, `app-resizability`, `building-document-based-swiftui-applications`, `audit-xcode-security-settings`, `adopt-c-bounds-safety`; the shift reported that several of them say in their first lines that they supersede prior training; the first project copied the SwiftUI, App Intents and xctrace ones into `~/.claude/skills` so its builders get them too. Whether they change outcomes is unmeasured so far.
- Builder subagents build in their own worktree but share the target's derived-data folder; serialize builds of the same target with `agentlock acquire build:<target>`.

## Verification

- Verify by observation: the screen, the state read back, the log line. A test that passes is not evidence that the behaviour is right; a screenshot or a read-back is.
- Anything racy (concurrency, background transitions, audio sessions) runs five to ten times.
- A negative result ("the dialog does not appear") needs a control in the same run that shows the dialog can appear.

## High-risk tier

Data and migrations, speech or audio session handling, background tasks, anything that touches the user's recordings or the on-device model's memory, StoreKit.
